Features

One bot, and it is good at the boring parts.

Most servers collect five bots and lose track of which one did what. Kernel is one member in your list, and the whole trail of evidence lives in one place.

01 · Guard

Anti-nuke that can put the server back

When channels and roles get deleted in a burst, Kernel can rebuild them. It keeps taking snapshots while it runs, so the restore point is recent even if nobody noticed the attack.

  • Channel names, topics, positions, permissions and the role list.
  • Burst detection on a configurable threshold and window.
  • Dry run with /antinuke restore preview:True.
  • Ships alert-only until you arm auto-response.

02 · Receipts

Moderation that keeps its receipts

Every warn, kick, ban, timeout and lock becomes a numbered case. Each case stores the fingerprint of the previous one, so editing history breaks the chain to the end.

  • /cases verify names the exact entry that no longer matches.
  • The head is mirrored in meta.json.
  • /cases export gives you an off-box copy.
  • Content, link, sequence and head damage are distinguished.

03 · Audit

Audit before you guess

/security audit scores your readiness, lists everyone holding Administrator and checks whether alerts can actually reach you.

  • Baseline the config, then get told when it drifts.
  • Watch channels for risky permission changes.
  • Weekly digest without opening a dashboard.
  • The output names what the check cannot prove.

04 · Toolkit

The rest of the toolkit

The guard features are the reason to install Kernel. These are the reasons you stop needing a second bot.

  • Automod — spam, caps, links, invites, words and mention floods.
  • Verification — a maths gate that keeps raid alts in a waiting room.
  • Logging — message, join, level-up, welcome and leave events.
  • Community — tickets, giveaways, polls, rank and afk.
  • Economy and games — cash, daily streaks, blackjack, slots and more.
  • Utility — userinfo, avatars, snipe, translate, embeds and socials.
Proof

Do not take my word for it. Spend two minutes on each.

A feature you cannot test is a feature you are guessing at. Here is the shortest honest test for the claims above, run in a throwaway channel.

Test 01 · the guard is awake

Run /antinuke status

You should see Monitoring only and a snapshot count like 11 channels, 7 roles. An empty snapshot means no restore is possible — that is the line that matters.

Test 02 · it reacts

Delete two throwaway channels

Lower the trigger once with /antinuke config threshold:2 window:20, delete two channels in a row, then set threshold:3 back. An alert naming the user should land in your alerts channel.

Test 03 · the receipts

Warn someone, then verify

/warn add gives a numbered case. Run /cases verify: it reports how many cases are chained and prints the head. Copy the head and keep it — that is your evidence.

Test 04 · tampering

Edit a case, on purpose

Stop the bot, change one word in a stored reason inside data/ledger.json, start it again, run /cases verify. It names the entry and the head is no longer the one you copied.

Setup

Three steps, then it guards on its own.

Kernel is a plain Node application. Anywhere Node 18 or newer runs, Kernel runs — your PC, a VPS or a free hosting panel.

1

Invite and point the channels

Add Kernel with the invite link, then /setlogs and /antinuke setup so alerts have somewhere to go. The first snapshot is taken the moment it joins.

2

Register who is allowed

/antinuke owner add for yourself, then exempt the bots and staff you trust. Until an owner is registered, Kernel reports but never acts.

3

Arm it deliberately

Drill once with /antinuke drill, then switch autorespond on. Turn on /security baseline and the weekly digest.

FAQ

The questions people actually ask before adding a bot.

Does Kernel need Administrator?

Anti-nuke restore and channel locks touch permissions across every channel, which in practice means a very high-privilege role. That is exactly why /security audit exists: it lists everyone who holds Administrator, including Kernel itself, so you can see what you granted instead of remembering it.

Give Kernel the least you can live with, and re-run the audit after any change.

What does it do the second an attack starts?

By default, nothing but an alert. Kernel ships in monitoring mode because a bot that acts on a wrong guess can lock out your own staff. When you turn auto-response on, Kernel can lock the channel, remove the offending role or kick the account, and it logs each of those as a numbered case.

Can a moderator edit the case history?

They can edit the file on the host — Kernel cannot stop someone with access to the disk. What they cannot do is get away with it. Editing one field breaks every hash after it and moves the chain head, and the head is mirrored in a second file. /cases export exists so you can keep a copy somewhere Kernel has no write access to.

Will my other bots still work?

Yes. Kernel uses slash commands only and never registers a text prefix, so there is nothing to collide with. It also stays quiet about messages it did not ask for; automod rules can be scoped to specific channels or exempted per role and per bot.

Is the data sent anywhere?

No. Configuration, cases, wallets and snapshots are written to local JSON files in the data/ folder next to the bot. There is no analytics endpoint and no third-party service. Backing Kernel up means copying that folder, and wiping it wipes the server's config.

What is Kernel not?

It is not a music bot, not an AI chatbot, and not a level system with role rewards yet. It cannot undo a channel delete — restore rebuilds an equivalent channel under a new id, so anything that referenced the old id needs pointing again. And it is a small project: if your server needs a support SLA, use a commercial bot.
